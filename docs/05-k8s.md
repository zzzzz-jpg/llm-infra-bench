## 2. 探针：三个探针各自的职责

```yaml
startupProbe:      # 独占冷启动窗口
  httpGet: {path: /health, port: http}
  periodSeconds: 10
  failureThreshold: 120      # 120 × 10s = 20 分钟预算
readinessProbe:    # 决定是否进 Service endpoints
  httpGet: {path: /health, port: http}
  periodSeconds: 5
  timeoutSeconds: 3
  failureThreshold: 2
livenessProbe:     # 决定要不要杀掉重启
  httpGet: {path: /health, port: http}
  periodSeconds: 20
  timeoutSeconds: 10
  failureThreshold: 3
```

### 2.1 为什么必须有 startupProbe

vLLM 的进程在**权重还在往显存里搬**的时候就已经在监听端口了。
如果只有 liveness + readiness，`initialDelaySeconds` 就必须设成
"最慢的那次冷启动"，而这会让**运行期**的故障检测也变慢同样多。
startupProbe 把两件事解耦：冷启动期间 liveness/readiness 完全不生效，
一旦 startup 成功，liveness 立刻以 20s 周期接管。

**把 `failureThreshold × periodSeconds` 设成实测冷启动时间的 2 倍。**
实测方法：
```bash
kubectl -n llm-inference get pod <pod> -o jsonpath='{.status.conditions}' | jq
# 对比 Initialized → ContainersReady 的时间差
# 或看引擎日志里 "init engine (profile, create kv cache, warmup model)" 到
# "Application startup complete" 的时间
```
冷启动时间的组成（每一项都可以单独优化）：

| 阶段 | 7B 典型耗时 | 优化手段 |
|---|---|---|
| 镜像拉取 | 0（已缓存）–10 min | 节点镜像预热、DaemonSet 预拉 |
| 权重读取 | 30 s（本地 NVMe）–10 min（网络 PVC @200MB/s） | **节点本地存储 / 每节点一份缓存**，这是最大杠杆 |
| CUDA 上下文 + profiling run | 10–30 s | 无法省 |
| KV 池分配 | 5–15 s | 与 `gpu-memory-utilization` 成正比 |
| CUDA graph 捕获 | 20–120 s | `--enforce-eager` 可跳过，但 decode 慢 10–30% |
| 就绪探针首次通过 | ≤ 5 s | — |

冷启动时间**直接决定 HPA 有没有用**：如果副本要 8 分钟才能服务，
而流量尖峰持续 3 分钟，那么自动扩容在数学上就无法应对这个尖峰。
这时正确的方案是常驻最小副本数 + 预热池，而不是调 HPA 参数。
告警 `InferenceStartupTooSlow` 就是为了让这个数字的退化可见。

### 2.2 readiness 用 `/health` 够不够？

不够，但它是可用的下限。更好的选择：

| 引擎 | 更好的就绪信号 | 代价 |
|---|---|---|
| vLLM | `/v1/models` 返回 200 且包含目标 model id | 仍不验证推理路径 |
| SGLang | **`/health_generate`**（真的跑一次生成） | 每次探测消耗一次推理，`periodSeconds` 不能太小 |
| 通用 | sidecar 定期发一次 `max_tokens=1` 的请求，把结果写成本地文件，readiness 读文件 | 最准确，也最复杂 |

**不要用 TCP socket 探针**：端口开着 ≠ 能推理。

### 2.3 liveness 的 timeout 必须宽松

`timeoutSeconds: 10` 而不是 1。原因：在超大 batch 的一次 prefill 期间，
API server 的事件循环可能被阻塞数百毫秒到数秒（取决于版本与是否开启
chunked prefill）。1 秒的 timeout + 3 次失败会把一个**正常工作但很忙**的
Pod 杀掉，然后在最忙的时候触发更多冷启动 —— 典型的死亡螺旋。

### 2.4 preStop + terminationGracePeriodSeconds

```yaml
lifecycle:
  preStop:
    exec: {command: ["/bin/sh","-c","sleep 20"]}
terminationGracePeriodSeconds: 120
```

`sleep 20` 的作用：Pod 被标记 Terminating 后，endpoints controller 需要
时间把更新传播到 kube-proxy / Ingress controller / 所有客户端连接池。
没有这个 sleep，就会有一批请求被路由到已经不再接受连接的 Pod，
表现为**每次滚动升级都有一小撮 502**。
`terminationGracePeriodSeconds: 120` 保证正在进行的长流式响应有时间写完
（2000 token @ 20ms = 40s，加上 prefill 与网络，120s 是安全值）。

## 3. 资源限额

```yaml
resources:
  requests: {nvidia.com/gpu: 1, cpu: "4", memory: 32Gi, ephemeral-storage: 8Gi}
  limits:   {nvidia.com/gpu: 1, cpu: "8", memory: 64Gi, ephemeral-storage: 16Gi}
```

| 项 | 依据 |
|---|---|
| `nvidia.com/gpu` | 扩展资源，request 必须等于 limit，不可超卖。它同时决定调度与配额 |
| `cpu: 4→8` | **CPU 在 TTFT 的关键路径上**：tokenize（prefill 前）与 detokenize（每个 token）都在 CPU。限到 2 核会让 TTFT 明显恶化，而且这个恶化看起来像 GPU 问题 |
| `memory: 32→64Gi` | 权重 staging（mmap 也占 page cache）、`--swap-space 4` GiB/序列的 CPU 换出池、tokenizer、Python 堆。**OOMKilled 而 GPU 看起来很正常**是最常见的困惑来源 |
| `ephemeral-storage` | HF cache、`/tmp`、torch inductor 编译产物。不设限会被 kubelet 驱逐 |
| `/dev/shm` 16Gi (emptyDir medium: Memory) | NCCL 用共享内存做节点内通信，默认 64MiB 会在 TP>1 时以 "Bus error" 崩溃 |
| `IPC_LOCK` capability | CUDA pinned memory。没有它，大块 prefill 会退化成可分页拷贝，TTFT 变差 |

### 3.1 一个反直觉的点：CPU limit 会影响 TTFT

`limits.cpu: 8` 意味着 CFS 配额 = 8 核·100ms/100ms。
detokenize 是逐 token 的 CPU 工作，在高并发下会和 tokenize、
HTTP 处理、metrics 采集抢这个配额。被 throttle 时表现为
**ITL 出现规律性的尖峰**（每 100ms 一次），看起来像 kernel 问题。
诊断：`container_cpu_cfs_throttled_periods_total / container_cpu_cfs_periods_total`。
如果这个比例 >5%，提高 CPU limit。

### 3.2 GPU 拓扑

```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule     # prod overlay
nodeAffinity: nvidia.com/gpu.product In [NVIDIA-A100-SXM4-80GB, ...]
```

两条都是**为了测量与生产的可比性**：
- 同一节点两个副本会共享 HBM 带宽之外的东西（PCIe、host 内存带宽、CPU），
  导致单副本压测结论无法外推。
- 混用 A100 与 L4 副本会让延迟分布变成双峰，
  任何单一 P99 阈值都无法描述它，告警必然误报。

## 4. 扩缩容

### 4.1 HPA 的信号选择

```yaml
metrics:
  - type: Pods      # 主信号：引擎队列深度
    pods: {metric: {name: vllm_num_requests_waiting}, target: {type: AverageValue, averageValue: "1"}}
  - type: Pods      # 负载信号：每副本 rps，目标 = 0.75 × 实测 knee
    pods: {metric: {name: inference_requests_per_second_pod}, target: {type: AverageValue, averageValue: "2.6"}}
  - type: Resource  # 兜底：custom-metrics API 挂了还能工作
    resource: {name: cpu, target: {type: Utilization, averageUtilization: 80}}
```

**为什么不用 CPU**：一个 GPU 副本可以在 15% CPU 下 100% 饱和。
CPU 只会让你在已经崩了之后才扩容。

**为什么 `averageValue: "1"` 而不是 0**：队列深度是整数且抖动大，
目标 0 会导致 HPA 永久震荡。目标 1 意味着"允许一个请求在等，
第二个就开始扩"，这在延迟与稳定性之间是合理的折中。

**为什么目标是 0.75 × knee**：knee 是 SLO 刚好达标的点。
在 knee 上运行意味着**任何**扰动都会违约。0.75 留出 33% 的裕度
吸收扩容期间的增长（扩容需要冷启动时间，这段时间流量还在涨）。

`averageValue: "2.6"` 这个数**必须**由 `capacity.py` 产出：
```bash
python3 bench/capacity.py bench/results --tag-filter <tag> --target-rps <X>
# 输出里直接给了 HPA yaml 片段
```

### 4.2 behavior：快涨慢跌

```yaml
scaleUp:   {stabilizationWindowSeconds: 60,  policies: [Pods:2/60s, Percent:100/60s], selectPolicy: Max}
scaleDown: {stabilizationWindowSeconds: 600, policies: [Pods:1/120s],                selectPolicy: Min}
```

不对称是有意的：
- **涨要快**：TTFT 在过拐点后是秒级恶化，扩容窗口以分钟计，必须立刻反应。
  `Percent: 100` 允许一次翻倍（1→2→4→8），比每次 +1 快得多。
- **跌要慢**：缩容丢掉的是**已经加载好的权重和已经预热的 prefix cache**。
  10 分钟的稳定窗口 + 每 2 分钟最多减 1 个，避免流量小幅波动就丢副本。

### 4.3 KEDA 替代方案

如果你的集群已经用 KEDA，可以用 `prometheus` scaler 直接按 PromQL 扩缩，
好处是支持 **scale-to-zero**（对内部工具类服务能省很多钱）和按时间预扩容。
代价是多一个组件、冷启动从"分钟级"变成"必须承受"。
**对生产流量不建议 scale-to-zero**：一次冷启动 5–10 分钟的 503 是不可接受的。
对内部 notebook / 评测集群非常合适。

### 4.4 配额与 maxReplicas 的一致性

```yaml
# 00-namespace.yaml
requests.nvidia.com/gpu: "8"
# 40-hpa.yaml
maxReplicas: 8
```

**这两个数必须一致**，否则 HPA 会把 desired 提到 12，
Pod 永久 Pending，而 `InferenceReplicasAtScaleCeiling` 告警
（HPA 触顶 **且** 队列仍在增长）会正确地把它报成容量事故。
`make lint` 的 overlay 检查会验证 prod overlay 里的 `maxReplicas: 8` 真的被应用了。

## 5. 告警 → Runbook

20 条告警在 [`observability/prometheus/alerts.yml`](../observability/prometheus/alerts.yml)
（裸 Prometheus）与 [`k8s/base/50-servicemonitor.yaml`](../k8s/base/50-servicemonitor.yaml)
的 `PrometheusRule`（集群内）。两份内容一致，前者是源。

### TTFT p99 above SLO {#ttft-p99-above-slo}

```
1. 看队列：sum(vllm:num_requests_waiting)
   >0 且持续 → 是容量问题，去 2
   ≈0        → 不是排队，去 3
2. 容量分支：
   - HPA 是否触顶？ kube_horizontalpodautoscaler_status_current_replicas == spec_max_replicas
     → 是：提 maxReplicas（先确认 ResourceQuota 和 GPU 节点池余量）；
           短期缓解：网关限流阈值下调到实测 fleet knee
     → 否：HPA 为什么没扩？kubectl describe hpa vllm 看 events；
           常见原因：prometheus-adapter 没数据（custom.metrics API 空）、
           或新 Pod 卡在 Pending（配额/节点不足/镜像拉取）
   - 冷启动太慢？ 对比 InferenceStartupTooSlow 告警与流量尖峰时长
3. 非排队分支：
   - prefix cache 命中率掉了？ inference:prefix_cache_hit_ratio:10m
     → 查路由是否失去了前缀亲和性，或刚发布过（缓存被清空）
   - 流量结构变了？ rate(vllm:prompt_tokens_total[5m]) / rate(request_success[5m])
     = 平均每请求 prompt token 数。上升 → 有人在发长上下文
   - GPU 降频？ DCGM_FI_DEV_SM_CLOCK 对比额定值，DCGM_FI_DEV_GPU_TEMP > 85
   - 引擎配置漂移？ alert BenchmarkConfigDrift / Grafana 的 config_hash 标签
4. 客户端交叉验证：引擎侧 TTFT histogram 与压测器客户端 TTFT 的差值
   突然变大 → 问题在网关（缓冲、超时、连接池），不在引擎
```

### KV cache near exhaustion

```
1. 立即：网关限流下调，或临时降低 --max-num-seqs（需滚动重启）
2. 查 preemptions：rate(vllm:num_preemptions_total[5m]) > 0 → 已经在浪费算力
3. 根因分支：
   - 长上下文流量增加 → 缩短 --max-model-len，或按上下文长度分流到不同池
   - prefix cache 占了太多块 → 权衡：命中率收益 vs KV 压力
   - gpu-memory-utilization 设太保守 → 提高（留 2-4GiB 给激活与碎片）
4. 结构性解法：--kv-cache-dtype fp8（并发上限 ~2x，需评估质量），
   或用 capacity_model.py 重新算 KV 预算再定 --max-model-len
```

### InferencePodCrashLooping

```
1. kubectl -n llm-inference describe pod <pod> | grep -A10 "Last State"
   Reason: OOMKilled   → 提高 memory limit（不是 GPU 显存！是容器内存）
                         检查 --swap-space 是否过大
   Reason: Error + 日志含 "Bus error"  → /dev/shm 太小（TP>1）
   Reason: Error + 日志含 CUDA OOM     → 降低 --gpu-memory-utilization 或 --max-model-len
   Exit Code: 137 + 无 OOMKilled       → 被 liveness 杀的，检查探针 timeout
2. XID：DCGM_FI_DEV_XID_ERRORS 或 dmesg | grep -i xid
   有 → 节点问题，cordon + drain，报修
3. 日志里的 "init engine" 之后崩溃 → 通常是 KV 池分配失败，
   说明卡上有别的进程占着显存（nvidia-smi 确认）
```

### HPA pinned at maxReplicas

```
这是容量事故，不是故障。
1. 确认：kubectl -n llm-inference get hpa vllm
2. 短期：网关限流下调到 fleet knee（实测 rps × 副本数）；
        对非关键租户降级（缩短 max_tokens、切到量化副本）
3. 中期：提 maxReplicas + ResourceQuota + GPU 节点池扩容
        ⚠️ 三者必须同时提，只提 HPA 会得到一堆 Pending Pod
4. 长期：用 capacity.py 的输出做容量规划评审；
        评估 prefill/decode 分离部署（decode 副本的 GPU 利用率通常高得多）
```

## 6. 滚动升级

```bash
# 引擎参数改了 → 必须让 Pod 真的滚起来
kubectl -n llm-inference annotate deploy/vllm \
  llm-inference/config-hash="$(sha256sum <(kubectl -n llm-inference get cm vllm-engine-args -o jsonpath='{.data.args\.txt}') | cut -d' ' -f1)" \
  --overwrite
kubectl -n llm-inference rollout status deploy/vllm --timeout=20m
```

ConfigMap 的修改**不会**自动重启 Pod。`make config-hash` 目标就是做这件事，
同时这个 hash 会作为 Prometheus 标签（ServiceMonitor 的 relabeling），
让 Grafana 能按"配置版本"切分面板 ——
这是判断"性能变化是不是发布导致的"最直接的证据。

`maxSurge: 1, maxUnavailable: 0` 要求升级期间**有一个空闲 GPU**。
如果配额刚好等于副本数，改成 `maxSurge: 0, maxUnavailable: 1`，
并接受升级期间容量减半（此时应该配合网关限流下调）。

## 7. Ingress 与流式响应

```yaml
nginx.ingress.kubernetes.io/proxy-buffering: "off"        # 必须
nginx.ingress.kubernetes.io/proxy-read-timeout: "600"     # > 最长生成时间
nginx.ingress.kubernetes.io/proxy-body-size: 32m          # 长上下文 prompt
nginx.ingress.kubernetes.io/limit-rps: "40"               # = fleet knee
```

- **`proxy-buffering: off` 是流式的前提。** 开着的话 nginx 会把响应攒起来，
  客户端看到 TTFT ≈ E2E，"打字机效果"完全消失。
  验证：`curl -N` 观察 token 是否逐个到达；或对比
  `sse_chunks == completion_tokens`（`verify_run.py` 会检查这个）。
- **`proxy-read-timeout` 必须大于最长请求时间。** 默认 60s。
  一个 4096 token 的生成 @ 20ms/token = 82s，会被拦腰截断，
  客户端看到的是连接重置，服务端日志里什么都没有。
- **限流阈值 = 实测 fleet knee**，不是随便填的数。
  429 是可控失败，KV cache 崩溃是不可控失败。前者永远更好。
- **不要把 `/metrics` 暴露到公网**：它包含容量、队列深度、GPU 型号与数量。

## 9. 故障演练（做过才算真的可运维）

在预发环境按顺序做，每次记录检测时间（告警触发）与恢复时间：

| 演练 | 命令 | 期望 |
|---|---|---|
| 负载下杀一个 Pod | `kubectl -n llm-inference delete pod <pod>` | PDB 不阻塞；HPA 补副本；期间 TTFT 短暂上升；`InferenceNoReadyEndpoints` **不**触发 |
| 全副本不可用 | `kubectl -n llm-inference scale deploy/vllm --replicas=0` | 1 分钟内 `InferenceNoReadyEndpoints` page |
| 超过 knee 施压 | `make bench SUITE=rate RATES="<2× knee>"` | `InferenceQueueBacklog` 在 2 分钟内触发，HPA 扩容，**不出现 5xx 雪崩** |
| KV 打满 | 发一批 32k 上下文的请求 | `KVCacheNearExhaustion` + `InferencePreemptionsOccurring` 触发 |
| GPU 故障 | 在节点上 `nvidia-smi -i 0 -rgc` 或注入 XID | `GPUXIDError` page，节点被 cordon |
| 配额不足 | 把 `maxReplicas` 提到超过 ResourceQuota | Pod Pending；`InferenceReplicasAtScaleCeiling` 触发（这个告警的价值就在于此） |
